# Phase 4 collaboration audit and run guide

Status: **OPEN**. P4-01 through P4-12 are implemented, but Phase 4 has failed and unrun mandatory exit proofs. This P4-13 audit records the state; it is not a release approval. The [evidence index](evidence/phase4/README.md) records the linear task and fix commits from base `353306913f59fd4470bb32463bae1a55a90f1c95`.

Run one API writer process for each database. It holds a PostgreSQL session advisory lock for its lifetime; a second process fails startup, and loss of that session terminates the writer. Route readiness probes to `GET /health/ready`, which checks the lock, database, required tables, and unapplied migrations. `GET /health/live` only confirms that the process is responding. Do not route new traffic to a process whose readiness probe fails.

Set `DATABASE_URL` to the pooled endpoint and `DATABASE_DIRECT_URL` to the direct endpoint for the same database and role. Configure `PUBLIC_API_ORIGIN`, exact `ALLOWED_WEB_ORIGINS`, `PORT`, and a 32-character-or-longer `BETTER_AUTH_SECRET`; web builds need matching `VITE_API_ORIGIN` and `VITE_WS_ORIGIN`. The API config validates these at startup. The room registry admits at most 20 active rooms per process, each room has a connection cap, and validation workers use bounded concurrency and queue depth. Admission rejects with `SERVER_BUSY` or `ROOM_FULL`; increasing process count is not supported by this single-writer design.

The API writes structured `collaboration.*` JSON events to stdout. Monitor `connections.activeSockets/activeRooms`, `admission_reject`, `access_reject`, `update_reject`, `validation_reject`, `db_write.durationMs`, `ack.latencyMs`, and `compaction.durationMs/snapshotBytes`. Client reconnect events report only a count. Rejection codes and worker failure kinds are bounded values; these events omit identity, graph content, cookies, and update payloads. Investigate a rising ACK latency or repeated admission rejects before increasing load.

For a rejected or unsaved board, keep its local copy and use **Download recovery**. **Reload server version** is a deliberate last step for a connected writer: the confirmation explains that pending changes in this account/board/device namespace will be deleted. Download first if those changes matter. Cancel preserves the namespace. Confirmation stops sync, deletes that namespace while the Web Lock is owned, and opens a fresh server copy; other board/account namespaces remain.

Temporary user direction for current implementation: skip browser-running checks. Do not run `pnpm phase4:quick`, `pnpm phase4:verify`, or `pnpm phase4:verify:legacy` while this pause applies; each can launch Chrome. Run focused non-browser format, lint, typecheck, build, unit, and integration commands instead. Record browser-dependent Phase 4 proofs as **UNRUN (deferred by user)**; Phase 4 remains OPEN. The full verifier is still the required later audit gate with ignored `.env` and `.env.local` containing paired database URLs. It runs each shared check once, creates isolated migrated schemas for database and served-browser exercises, and returns nonzero on any child failure or missed measurement target. These commands write detailed child output to a temporary log directory and print concise results; pass `-- --verbose` to a script for full output. See [P4-12 evidence](evidence/phase4/P4-12.md) for the observed gate status and acceptance matrix.

For a narrow edit during the pause, run a focused non-browser check such as `pnpm --filter @archboard/api test -- validation-worker`. `pnpm test:browser -- web-lock-broadcast-channel` remains available for the later browser audit. Do not run the full gate until browser verification resumes.

## Measurements and limits

The [shared limits](../packages/contracts/src/limits/index.ts) cap the live graph at 500 nodes, 1,000 edges, 50 boundaries, and 50 steps; accepted encoded state at 10 MiB; decoded client updates at 1 MiB; WebSocket frames at 16 MiB; connections at 10 per board and active rooms at 20 per process. Update admission is 20/second sustained with burst 40. Presence is 15/second per connection and expires after 30 seconds. Validation has two workers, a 20-job queue, and a two-second timeout. Dirty-room compaction triggers after 200 updates or 60 seconds; idle eviction waits five minutes.

[P4-12](evidence/phase4/P4-12.md#focused-runs-and-measurements) measured five independent authenticated headless-Chrome contexts on Windows, Intel i5-9300H, eight logical CPUs, 17.0 GB RAM, Node 22.23.2, a 200-node seed, and a CDP 100 ms network-latency setting. Twenty all-peer edit-visibility samples gave **6,598 ms p95 versus the 500 ms target: FAIL**. Five cached openings gave **1,886 ms p95 versus the two-second target: PASS**. Server event samples gave 567 ms p95 database writes and 8,752 ms p95 ACK latency. The CDP setting was not separately verified as transport RTT; the database endpoint is remote. Typical/limit worker validation medians were 439.8/499.4 ms, with maxima 495.67/543.73 ms, below the two-second validator budget. No same-region staging claim follows from this local measurement.

The P4-13 current-tree rerun used the same five-user, 200-node, 20-edit script and CDP latency setting. All-peer visibility was **4,876 ms p95 versus 500 ms: FAIL**; five cached openings were **1,233 ms p95 versus two seconds: PASS**. Bounded server samples were 627 ms p95 database write and 8,088 ms p95 ACK. The typical/limit worker measurement passed its two-second validator budget. These are local observations, not a measured same-region RTT.

## Gate status and next work

The exit gate is **OPEN** because the measured collaboration visibility budget fails; a literal post-commit/pre-ACK API process kill and lock-session-loss termination have not been proved; combined A10, socket-level A23, and socket/database A30 proofs are unrun; a served storage-error recovery observation is missing; the configured root database reports `RetainCompactedUpdateReceipts1790426800000` unapplied; and `pnpm boundary:check` reports collaboration application-to-infrastructure and cross-feature imports. These are reproducible blockers, not waived checks. Apply the forward migration only to the intended environment after reviewing its target; then rerun `pnpm db:migration:show`. Resolve the boundary findings without weakening the checker, add the missing fault and browser harnesses, investigate the measured ACK/visibility path, and rerun `pnpm phase4:verify` under a recorded same-region environment and measured RTT **after browser verification resumes**. Keep the separate Phase 2 audit open until its own evidence is complete.

Phase 4 proves synchronized editing when the app assets are available. The Phase 5 offline route shell, Phase 6 sharing/discussion UX, Phase 7 presentation/portability, and Phase 8 release hardening remain outside this gate. A local merge into `main`, when requested, integrates the branch but does not change this OPEN decision.
