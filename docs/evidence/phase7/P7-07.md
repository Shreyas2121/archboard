## Contracts used

Capture requires the current active owner/editor, a trimmed 1–120-character name and exact
decimal `expectedSeq`. Actor/session identity is supplied by authenticated HTTP handling;
the session is rechecked after transaction lock acquisition and after worker reconstruction.
The server cannot establish absence of undisclosed client edits. Online/settled persistence/
acknowledged outbox gating remains P7-08 client work.

An exported collaboration application port uses the existing room queue when active/opening;
it does not create a room for REST alone. The board row lock serializes closed-room capture
with durable writes, archive/access changes and compaction. Creator/private initialization
use the existing actor-before-board lock order. Committed capture reads the complete bounded
snapshot/log pair through the same transaction manager, checks continuity through the locked
sequence, and reconstructs through the existing validation worker with remapping disabled.
No in-memory room candidate is captured. No graph sequence, graph timestamp, update receipt,
outbox, ACK or update message is created by checkpoint capture.

Sequence conflicts and the 100-checkpoint cap apply to new effects. Existing 24-hour
actor/operation UUID receipts commit metadata/bytes/result together and return the original
successful response after source advancement or at cap; changed requests conflict. Current
session/role/archive authority is checked before receipt lookup. Notifications for
`checkpoints` occur only after a new committed creation, outside the capture queue to avoid
re-entering that queue while it is held. Replay/denial/rollback emits no successful hint.

Detail derives a strict portable projection from validated immutable bytes without editing
the record/source. Any current reader, including a viewer of an archived source, may inspect
and restore. Restore rechecks source authority and board-scoped checkpoint existence even
on replay. It projects, remaps and hydrates a new document through P7-06, then calls the same
transaction-scoped private initializer. Title comes from the request; description is current
source metadata because checkpoint records store graph bytes rather than board metadata.
Source graph IDs/history/access/discussion/checkpoints are never copied into the new namespace.

## Schema and API impact

Existing `checkpoints` entity/table/index are reused unchanged. Migration source includes
UUID IDs, board FK, restricted creator FK, decimal nonnegative sequence, bytea, server creation
time and `(board_id, created_at, id)` indexing. No forward migration gap was found; no configured
schema/migration inspection or migration execution occurred.

Implemented `/api/v1` routes matching `plan.md`/`phase7.md`:

- `GET /boards/:id/checkpoints`: metadata only, newest timestamp/UUID first, 30 default /
  100 maximum, microsecond-preserving cursor and `nextCursor`.
- `POST /boards/:id/checkpoints`: name/expectedSeq, UUID `Idempotency-Key`, immutable metadata
  response, 201; sequence/changed-key/archive conflicts 409, role denial 403, unknown source
  404, checkpoint cap 413.
- `GET /boards/:id/checkpoints/:checkpointId`: metadata plus validated graph projection;
  both IDs scope lookup; no bytea is returned.
- `POST /boards/:id/checkpoints/:checkpointId/duplicate`: title, UUID `Idempotency-Key`,
  fresh private board summary, 201; this is the restore-as-new action.

Checkpoint responses use `Cache-Control: no-store`. Shared DTOs and OpenAPI components agree;
no checkpoint edit/delete/live-rollback endpoint exists. Creator/time/sequence/schema/ownership
cannot be supplied as writable fields. Corrupt/oversized stored content yields safe errors.

## Security and account evidence

All lookups bind checkpoint ID together with the source board and current authority.
Private results derive ownership from the actor. Session checks occur after waiting for locks
and after bounded worker work; protected receipt replay rechecks current source authority.
Lists exclude graph bytes and content; detail exposes graph DTOs only. Safe errors exclude
database/worker internals. No new network fetch/execution of graph content is introduced.

## Recovery and graph preservation evidence

Capture does not observe/clear local pending edits. `throughSeq` states its committed boundary;
the client must explicitly synchronize or export pending local content separately. Restore
initializes a fresh board/document rather than replacing the original, so old offline clients
continue addressing their original account/board namespace. Uncertain retries retain the
original request/key and successful receipts; changed captures require explicit new requests.
