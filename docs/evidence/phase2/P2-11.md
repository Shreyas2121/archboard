## Behavior proved

- A validated, version-controlled `web-application` template contains Browser, API service,
  Database, Cache, request-payload code card, HTTPS/SQL/cache connections, a Backend boundary, and
  four request-path presentation steps. Instantiation remaps every entity ID and every edge/step
  reference through the shared graph schema.
- A writable first use distinguishes an empty namespace before its baseline is written, displays
  `Preparing local demo…`, creates the fixture through document-model commands, and does not expose
  the projection or `Saved on this device` until every fixture update commits. Existing local state
  hydrates without reseeding.
- Confirmed reset keeps the exact writer Web Lock, detaches and closes the old adapter/document,
  deletes all four stores only for the exact namespace, opens a fresh document, persists a freshly
  remapped fixture, clears selection/history, and announces reset only after persistence succeeds.
  Read-only tabs rehydrate after the reset hint without gaining writer authority.
- Recovery download validates the current strict projection and emits escaped JSON with the
  `archboard-local-recovery-v1` marker, ISO creation time, and `local-only` state. The browser object
  URL is revoked after the download starts; the UI makes no import claim.
- The top bar offers recovery whenever a projection exists. The reset dialog explains exact local
  replacement and offers recovery before confirmation. Storage failure retains canvas viewing,
  selection/inspection, viewport controls, and recovery while disabling every mutation control.
- The rendered A01 local flow created and renamed two component cards, connected them with the
  keyboard connection dialog, observed device save, reloaded, and preserved both IDs, all content
  and geometry, plus the edge ID and endpoints.

## Contracts used

- Namespace identity remains deployment origin + reserved `local-demo` user key + stable demo board
  UUID + graph schema version. Reset delegates to the existing exact-namespace deletion operation.
- The writer session remains the only owner of Web Lock, adapter, document replacement, and reset
  notification. React never opens IndexedDB or mutates Yjs roots.
- Fixture construction uses `graphProjectionSchema`; durable creation uses
  `createGraphObjects`/`createPresentationStep` with fresh application UUIDs and existing structural
  origins.
- Save/error phases come directly from the persistence external store. Recovery serializes
  `GraphProjection` only and does not include tombstones, permissions, transport state, or an import
  format claim.

## Browser evidence

Installed Google Chrome drove the served production `/demo` route through real Web Locks,
IndexedDB, downloads, and reloads. The temporary observer script and preview servers were removed or
stopped after the run.

- First use visibly reached `Preparing local demo…`, then `Saved on this device`, and rendered six
  canvas objects: five cards plus one boundary.
- Recovery parsed as 5 nodes, 3 edges, 1 boundary, and 4 presentation steps with the required marker
  and local-only status.
- Reload retained every fixture ID. Confirmed reset produced the same counts with no old rendered ID
  reused.
- A separate A01 product run created `A01 first` and `A01 second`, connected them through the
  keyboard dialog, waited for device save, reloaded, downloaded the strict projection again, and
  compared exact node content/geometry plus edge ID/endpoints successfully.
- Both runs observed zero WebSockets and zero `/api/` or GraphQL graph requests.

## Failure injection

The product run replaced native `IDBObjectStore.prototype.put` only for the next `localUpdates`
write, then created a component through the rendered palette. The UI entered
`Storage error · export your changes`, all mutation controls became disabled, no later saved label
appeared, and recovery download contained six nodes, including the failed write's in-memory card.
The browser context was then discarded; no production failpoint or test hook was added.

## Accessibility evidence

- Reset uses the checked-in dialog primitive with title, destructive explanation, recovery action,
  Cancel, and explicit confirmation. Its controls expose native disabled states while replacement is
  pending.
- Reset and recovery are named semantic buttons. Status changes use the existing polite live region;
  the Preparing phase is held briefly so it is not skipped by immediate React batching.
- Broader keyboard and screen-reader verification remains owned by P2-12.
