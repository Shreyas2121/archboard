## Behavior proved

- The exclusive writer-lock name is the versioned `archboard:writer:v1:` prefix plus the fully
  resolved deployment-origin/user/board/schema namespace. Acquisition uses `ifAvailable` and never
  requests stealing or a fallback lease.
- A lock owner holds the Web Lock until its adapter flushes pending writes and the session enters
  releasing. Only after the lock request finishes does it broadcast the release hint and close its
  channel.
- Session snapshots explicitly represent opening, writer, read-only-held-elsewhere, unsupported,
  releasing, and closed. Writability also reflects the underlying persistence edit guard.
- Only a writer can obtain a writable Y.Doc/persistence binding or execute a command callback.
  Read-only sessions expose projection access and hydrate through an adapter mode that performs no
  checkpoint, compaction, local observer attachment, local-log write, or outbox write.
- Cache-changed, reset-complete, and lock-released are the only BroadcastChannel hint types. Hints
  carry the exact namespace and protocol version; they do not contain Yjs updates and cannot confer
  ownership.
- A lock-release hint is the only automatic retry trigger. Retry first closes the stale read-only
  adapter/document, attempts the same non-stealing lock, creates a fresh document, rehydrates and
  validates committed IndexedDB bytes, and only then publishes writer/writable state.
- Unsupported Web Locks hydrate read-only without using localStorage. Explicit retry, route-style
  close, pagehide, partial initialization, and repeated close calls share idempotent cleanup.
- Two independent same-origin Chrome windows prove A12: the first alone mutates; the second reports
  read-only and creates no local update; a forged release hint cannot bypass the held lock; after
  clean release, the second acquires ownership and sees the first window's committed node before it
  becomes writable.

## Contracts used

- Storage and ownership share the canonical deployment origin + reserved local-demo user key +
  application UUID board ID + graph schema version namespace.
- The Web Locks API is the correctness boundary. BroadcastChannel is advisory and is never checked
  as proof of ownership.
- `LocalPersistenceAdapter` remains the hydration/validation and persistence barrier. Its new
  explicit read-only mode reuses the same replay validation while suppressing every durable write
  and returning an editing-paused ready snapshot.
- Session and persistence snapshots are immutable external-store values. The Y.Doc remains the
  durable graph source and is exposed for mutation only through an owned writable binding.

## Browser evidence

The A12 test opens two actual `window.open` pages at the Vitest/Playwright same-origin server. Chrome
reports the versioned lock as held. The first page persists a node; the second rejects its mutation
and leaves the namespace's local-update count unchanged. After release, the second page's writer
state is observed only after its projection contains that committed node, and its subsequent write
adds the second durable outbox record.

The browser suite also verifies native BroadcastChannel delivery for cache-change, reset, forged
release, and genuine release hints, plus native IndexedDB read-only hydration.

## Failure injection

- A forged, correctly shaped lock-release hint is sent while the first page still owns the lock.
  The second page closes its stale view and retries, but `ifAvailable` returns no lock; it rehydrates
  read-only and remains non-writable.
- A `lockManager: null` capability injection proves the unsupported-Web-Locks state exposes no
  writable binding and command execution throws `WriterLockRequiredError`.
