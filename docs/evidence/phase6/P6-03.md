## Behavior proved

Three new routes edit/delete messages and resolve/reopen threads through the existing
board permission service, transaction manager, shared schemas, and safe HTTP boundary.
Owners can moderate any message; current editors can moderate their own messages.
Original authorship and creation context remain intact under owner moderation. Viewers,
including downgraded former authors, cannot mutate. Removed/nonmember users and
cross-board resources return 404. Archived boards retain authorized reads and block
all three mutations. The real-session tests also cover session expiry while waiting
for the board lock and transactional downgrade/removal/archive before a waiting edit.

Resource-specific compare-and-set updates prevent lost updates. Real HTTP/database
tests prove edit/edit, both edit/delete orderings, and both resolution/reopening
orderings. Assertions inspect the winning stored body, version, author, and lifecycle
metadata after the stale request receives 409; they do not substitute status-only
proof for A20. Message mutations leave thread versions unchanged; resolution leaves
message versions unchanged. Editing leaves graph sequence and content timestamp intact.

Deletion stores the marker in the existing row, preserves author/creation/previous edit
metadata, and retains message counts/latest marker summaries. A deleted message cannot
be edited into live content, including with its current version. Repeated deletion at
the current version preserves the exact deletion timestamp and version. Resolution
records the acting user and database time; reopening clears both resolution fields.

## Contracts used

- PATCH message: strict `body, expectedVersion`; DELETE message: strict
  `expectedVersion`; PATCH thread: strict `resolved: boolean, expectedVersion`.
  Shared positive integer versions, UUID paths, 4,000-code-point body limit, and
  standard envelopes remain unchanged. Unknown authorship, lifecycle timestamp,
  creation version, resolution actor/time, and creator fields are rejected.
- Authorization and scoped resource lookup precede version checking. A viewer does
  not gain authority from old authorship; a cross-board ID never authorizes a row.
- A stale version always returns 409 `VERSION_CONFLICT`, even if the submitted state
  already matches. Successful changes increment only the affected resource version.
  An identical live body, already-deleted message, or unchanged resolution at the
  current version returns 200 with unchanged metadata/version. Deleted-message edits
  return 409 even at the current version. These rules are documented in Swagger.
- Edits set server `editedAt`; deletion sets server `deletedAt` and marker body without
  changing `editedAt`. Resolution sets `resolvedAt/resolvedBy`; reopening sets both
  null. PostgreSQL supplies times, and existing microsecond serialization is reused.
- These versioned mutations do not add creation-style idempotency keys. P6-02 creation
  receipts, caps, pagination, committed anchors, and exact retry behavior are unchanged.
- Unknown database errors reuse the established safe 503
  `TEMPORARILY_UNAVAILABLE` envelope. Tests check that injected SQL constraint names
  and submitted content do not appear in error responses.

## Schema and API impact

No schema changes or new migration. Existing message/thread integer versions and
nullable lifecycle/resolution fields satisfy this task. Tests migrate their own schema
with foundation and retention migrations and `synchronize: false`; existing discussion
indexes remain in place. No configured database migration is applied.

All new successful mutations return HTTP 200 with a standard object envelope:

- `PATCH /api/v1/boards/:id/comments/:commentId` — updated comment
- `DELETE /api/v1/boards/:id/comments/:commentId` — retained deletion-marker comment
- `PATCH /api/v1/boards/:id/threads/:threadId` — updated thread

Discussion now has seven operations. No hard deletion, previous-body history,
notification protocol, offline mutation sending, or moderation UI is added.

## Database, session, and socket evidence

Mutation ordering: validate body/path and initial cookie session; begin transaction;
lock board through centralized authority reader; recheck current session and role/archive;
read the subordinate record through its board; check owner/authorship where required;
check resource version and marker/current state; recheck session before a changed write;
execute conditional update; project response through the same manager; commit. The
existing board lock orders mutation, graph, membership, and archive changes; SQL version
predicates additionally guard the actual write. No unrelated resource version increments.

The edit/edit race uses independent concurrent owner/editor HTTP requests. Ordered
edit/delete and resolution/reopening races wrap the actual repository method solely to
hold its real PostgreSQL update before commit, then wait for PostgreSQL-reported board
lock contention from the competing request. No database result is mocked. Stale losers
cannot overwrite the stored winner. Access/session races likewise wait for an actual
lock wait before committing the authority change or expiring the real session.

Each rollback case installs a temporary NOT VALID false CHECK constraint in its isolated
schema, invokes the actual HTTP mutation, then asserts stored body/version/timestamps,
thread state, and receipt/row counts are unchanged. Constraints are removed in finally;
applications/connections close before the test schema is dropped.

No socket invalidation is implemented or claimed here; P6-04 owns post-commit hints.
