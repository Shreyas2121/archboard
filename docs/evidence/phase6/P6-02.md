## Behavior proved

The four discussion read/create routes use real Better Auth cookies, board-scoped
permissions, existing relational tables, and PostgreSQL transactions. Thread creation
stores the thread, first message, and replay receipt atomically. Replies use the same
receipt mechanism. Current owner/editor access permits creation; viewers read, including
archived discussions, but cannot write. Removed/nonmember users and cross-board thread
IDs receive 404. Downgrade, removal, and archive are rechecked before returning a stored
creation response. Session expiry while waiting for the board lock returns 401 without
rows or receipts.

The discussion integration suite exercises actual HTTP requests, authenticated accounts,
independent database connections, accepted graph updates, and database lock waits. The
fixture has two nodes and one edge per graph board. Cap fixtures contain 1,999 threads or
499 messages before two competing requests; deleted marker rows count toward each cap.
Final successful counts are exactly 2,000 threads and 500 messages, with one competing
request rejected at each boundary. Exact replay still succeeds at the cap.

Node/edge context comes from the accepted snapshot and contiguous update log under the
existing board lock. Forged wire labels/positions are ignored. Missing, other-board,
unsubmitted local-only, tombstoned, and missing-endpoint targets are rejected. Two ordered
graph deletion races prove that deletion committed first rejects creation, while creation
committed first retains its anchor and readable discussion after deletion. Exact replay
after deletion returns the original creation result. Discussion creation leaves graph
snapshot bytes, graph sequence, content timestamp, updates, and graph receipts unchanged.

Injected real PostgreSQL constraint failures at first-message insertion, thread receipt
insertion, and reply receipt insertion prove rollback. The first two leave zero discussion
rows/receipts; the third retains only the original thread/message. Removing each synthetic
test constraint permits an explicit retry with the same key.

## Contracts used

- Strict P6-01 schemas reject unknown authorship/time/version fields, invalid IDs, blank
  bodies, oversized bodies, invalid point coordinates, malformed cursors/filter/limits,
  and missing idempotency keys before writes. Accepted whitespace is preserved. Both
  creation routes accept 4,000 supplementary Unicode code points and reject 4,001.
- Node fallback uses accepted title and world position. Edge fallback uses accepted label
  and the midpoint of endpoint node centers. Derived coordinates must satisfy the shared
  bounds; the wire context never supplies fallback authority.
- Creation versions start at one; PostgreSQL provides timestamps. Thread summaries expose
  safe author/creator/resolver summaries, message count, latest message, and marker state.
  Original deleted bodies are sanitized to `Message deleted` at the read boundary.
- Threads order by `(createdAt,id)` descending; comments ascend. Resolved filtering and
  default/max page sizes 30/100 reuse shared contracts. Microsecond timestamps survive
  serialization and cursor encoding; tied timestamps use UUID order with no skipped or
  repeated rows in the integration fixture.
- Receipts use the existing actor/operation/key primary key, canonical request hash,
  response/status storage, and database 24-hour expiry. Board/thread target IDs are part
  of the operation. Concurrent duplicate callers create one effect and get identical
  results; changed body or anchor conflicts. Actors, boards, operations, and reply targets
  are independent. An explicitly expired receipt permits a new effect on an explicit
  request; no automatic client retry after expiry is implemented or implied.
- Error envelopes/statuses reuse the central boundary. Optional `fieldErrors` are not
  emitted by the existing validator. Caps return 413, missing committed targets 400,
  viewer writes 403, archive writes 409, and expired sessions 401.

## Changed scope

- Boards owns the new thin `DiscussionController`, application service/persistence port,
  repository, PostgreSQL adapter, provider wiring, `editDiscussion` permission operation,
  and integration suite. Discussion is subordinate to the existing board feature; a
  second feature module or permission/idempotency system was unnecessary.
- Existing `IdempotencyService.execute` gains an optional authorization callback before
  replay lookup. Existing consumers retain their call shape. The new consumer uses the
  callback to lock and reauthorize the board before disclosing a stored result.
- Collaboration exports a committed-anchor reader port and registers an adapter over the
  existing committed graph reader and bounded validation worker pool. It creates no
  graph store and writes no Y.Doc data.
- Auth's application facade exports the existing guard/decorator; its internal imports
  use their owning files to avoid a facade cycle. Discussion rechecks the existing session
  lookup after lock acquisition and after graph validation before writing.
- OpenAPI registers exactly the implemented GET/POST operations, schemas, pagination,
  cookie security, idempotency header, creation status, and error responses. Units verify
  that moderation routes remain absent. This evidence accompanies the implementation.

## Transaction and database proof

Mutation ordering is: validate HTTP wire input and initial session; begin transaction;
take existing transaction advisory lock for actor/operation/key; lock board through the
central permission reader; recheck current session, role, and archive; validate thread
scope for replies; inspect live receipt and request hash; return exact replay or remove
expired receipt; count cap rows; reconstruct/validate committed anchor for new threads;
recheck session; insert thread/message or reply; read creation DTO; store receipt in the
same transaction; commit. The board lock serializes cap counts with inserts, accepted
graph changes, archive, and membership changes. Receipts and effects roll back together.

Reads also acquire the existing board lock and recheck the session before selecting
board-scoped rows. No mock repository substitutes for transaction or race evidence.
Tests wait for PostgreSQL-reported row lock waits rather than assuming a request has
reached its boundary. Graph races use the production durable update service and existing
commit failpoint; the creation-first barrier wraps the real committed-anchor reader.
Test schemas are uniquely named and dropped after closing applications and connections.
