## Behavior proved

Implemented owner-only editor/viewer invitation controls inside the existing Share
dialog. Owners can create, explicitly copy or manually select the fresh link, browse
cursor-paginated metadata, and confirm revocation. Lists show creator, role, creation
and expiry timestamps, active-at-fetch/expired/revoked/consumed state, loading/error
states and cached-data age. Never-fetched data is unavailable rather than an empty
list. Existing Dialog/Select/Input/Label/Button primitives supply controls; the share
dialog scrolls on small screens. Rendered keyboard/accessibility proof remains UNRUN.

Creation and revocation refresh metadata/members before checking current owner,
account, connectivity and archive authority. Success and uncertain outcomes reconcile
the owner's invite query directly, without requiring a socket event or adding a wire
resource. Pending invite actions block member actions and duplicate submissions.
Definitive rejection, uncertain outcome, committed-but-refresh-failed and successful
revocation have distinct messages. Clipboard failure keeps the current fresh link for
manual copy. Closing/discarding the result, identity loss or scope disposal removes
the link from view; safe lists cannot reconstruct it.

An uncertain create retains its exact role, UUID key and start time in memory across
dialog closing. New creation is blocked until explicit same-request reconciliation.
A replay with unavailable URL identifies the original result and explains metadata
review, revoke and replacement. Retry stops after 23 hours, leaving margin before
the server's 24-hour retention boundary; an explicit successful list review is then
required before starting a new logical request. There is no automatic POST retry on
reconnection or background query refresh. Reload limitations are stated in the UI.

Eight P6-06 Node cases exercise actual invite adapter/hook source with synthetic
state/query/clipboard ports and real contract schemas. They prove owner blockers,
retry bounds, exact-role/key recovery, concurrent-submission blocking, response
uncertainty, clipboard fallback, safe DTO rejection, list reconciliation, and late
old-account/disposed response suppression. They do not render React or prove live
HTTP, browser storage, PostgreSQL transactions or session revocation.

## Contracts used

- Existing `/api/v1/boards/:id/invites`: GET safe paginated collection, POST validated
  editor/viewer role with `Idempotency-Key`, DELETE scoped invite with 204 response.
- Phase 3's token hashing, seven-day expiry, single use, replay redaction and permission
  services remain authoritative. Frontend lists reject token/link/hash fields through
  strict shared response schemas. Creator names render as plain text.
- Account/deployment/board/resource query keys reuse P6-04. Creation results bypass
  TanStack Query and mutation caches; only metadata pages enter invite queries.
- Existing P6-05 fresh authority checks and global API session-expiry handling are
  reused. A missing invite does not itself mark the owner's board access removed;
  authoritative metadata/member refresh handles current board access.
