# C11 - Prove durable commit-before-ACK behavior

## Behavior proved

The narrow collaboration persistence harness serializes proposals for one accepted board document. It authenticates the session and checks current owner/editor authority before looking up a receipt, hashes the exact update bytes with SHA-256, and returns a committed receipt only when board ID, update ID, actor, and payload hash all match. An authorized actor or payload mismatch returns `UPDATE_ID_REUSED`; anonymous and viewer retries do not disclose the receipt.

New bytes are applied only to an isolated Y.Doc candidate. Causal-completeness and complete document validation run against that candidate and the previously accepted document. Invalid physical state and missing Yjs causal dependencies leave the accepted state and PostgreSQL update log unchanged.

The real PostgreSQL path locks the board row, rechecks both archive state and write authority, increments the `bigint` sequence, inserts the exact `bytea` update and its receipt, and updates `content_updated_at` in one transaction. The candidate replaces accepted in-memory state only after the transaction commits. ACK and broadcast eligibility exist only in the successful post-commit return value. Concurrent proposals produced sequences `1` and `2` in serialized order while retaining both graph edits.

The integration suite creates a process-scoped PostgreSQL schema, migrates it from empty, and removes only that schema in cleanup. It does not reset or mutate tables in the database's public schema.

## Failure injection

`DATABASE_COMMIT` is reached after all transaction writes but before commit can succeed. Its deterministic failure rolls back the sequence increment, update, receipt, and content timestamp; no eligibility result is returned and the accepted Y.Doc bytes remain unchanged.

`AFTER_COMMIT_BEFORE_ACK` throws only after PostgreSQL commit and accepted-state promotion. The first attempt therefore returns no ACK, while its retry returns the original sequence, actor, hash, and creation time with ACK eligibility, no rebroadcast eligibility, and exactly one update and receipt. This proves A08.

The `AFTER_VALIDATION_BEFORE_TRANSACTION` control point revokes editor membership or archives the board after the optimistic authorization check. The row-lock transaction recheck rejects both cases without persistence or accepted-state mutation.
