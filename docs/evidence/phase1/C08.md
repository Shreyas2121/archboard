## Behavior proved

The API now uses an explicitly registered TypeORM entity set with `synchronize: false`. Ordinary runtime work uses the pooled `DATABASE_URL`; migrations and the singleton collaboration-writer session use `DATABASE_DIRECT_URL`. Better Auth owns a separate bounded `pg.Pool` and uses its official built-in PostgreSQL adapter.

The initial migration installs the pinned Better Auth schema before application foreign keys, followed by the ten Phase 1 application tables and their required indexes. Better Auth user identifiers remain `text`, Yjs payloads use `bytea`, and PostgreSQL `bigint` sequence fields are mapped as strings rather than JavaScript numbers.

The integration suite reset the disposable `production/neondb` public schema at the project owner's direction, migrated it from empty, and observed all four auth tables plus all ten application tables. It round-tripped `9007199254740993` without numeric conversion and round-tripped binary snapshot bytes exactly.

## Failure injection

One direct session acquires the PostgreSQL advisory lock while a second owner is rejected. After orderly release, a replacement owner acquires the same lock. A deterministic unit test emits the underlying session's connection-error event and proves readiness fails immediately, without relying on a timing-sensitive forced backend termination.

The schema-drift check creates an isolated temporary PostgreSQL schema, runs the pinned Better Auth CLI against it, compares normalized generated SQL with the committed artifact, and removes the temporary schema in cleanup.

## Connection behavior

The verification used the project's pooled runtime URL and direct migration URL without recording either credential. Pool bounds and connection timeouts are validated named settings. The user chose the disposable production branch for the portfolio build because current data is nonessential; future environments with valuable data should restore the branch-per-change workflow.

## Known gaps

The current pinned `pg` stack warns that `sslmode=require` semantics will change in pg 9. The present pg 8 behavior verifies the server certificate; a future major upgrade must deliberately choose `sslmode=verify-full` or libpq-compatible behavior and rerun these checks.

CRUD APIs, Better Auth HTTP/WebSocket integration, room persistence, and application-level migration orchestration remain outside C08.
