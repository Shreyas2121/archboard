## Implementation

Nest `WsAdapter` and `@nestjs/platform-ws` own the WebSocket server and gateway lifecycle. An HTTP upgrade broker matches `/ws/boards/:boardId`, validates exact configured Origin, resolves a real Better Auth session cookie, checks board read access, and only then upgrades. The gateway requires a strict `hello` within five seconds and rejects unsupported versions, binary/malformed frames, and excess frames without exposing graph state. It checks access again when joining, reserves a bounded room connection, serializes the join under the room queue, and sends a full `ready` snapshot and sequence. Subscribers registered during join buffer later committed updates until the ready send completes. Ping/pong liveness and safe error codes are wired. Client update, presence, and presenter behavior remain for later milestones.

## Verification

- Real PostgreSQL socket integration with actual Better Auth signup cookies: **11 passed**. Authorized owner received a parseable full Yjs graph at sequence 0. Anonymous, invalid-cookie, expired-session, forged-origin, nonmember, and missing-board cases disclosed no graph. Bad version, absent hello, malformed envelope, frame cap, and 11th room connection were rejected.
- Deterministic room test proved a commit queued after a join was buffered until ready activation, then delivered in sequence; **5 room tests passed**.
- Combined auth, board, invitation, REST boundary, and socket integration regression: **5 suites / 37 tests passed** before the added expired-session case. The focused socket rerun afterward passed all 11 tests.
- `pnpm.cmd --filter @archboard/api build`, `pnpm.cmd --filter @archboard/api typecheck`, `pnpm.cmd lint`, and `pnpm.cmd format:check`: **passed**.
- Better Auth schema check against an isolated PostgreSQL schema: **passed**, generated SQL matches committed SQL.

Each database integration suite used an isolated temporary schema on the existing direct PostgreSQL connection and removed it afterward. No production board data was read or changed. The 10-connection bound is observed through live sockets; one failed initial capacity run exposed a successful `ws.send` callback with a null error value. The gateway now accepts that success value and the full suite passes. The intended implementation does not persist or acknowledge client updates.
