## Behavior proved

Owner-only archive and restore use the board row lock, expected metadata version, database timestamps, and a repeat-state no-op. Restore also locks the owner user before the board and enforces the active owned board limit. A stale version conflicts even when the requested state already exists. Existing memberships survive archive and restore.

Any reader can duplicate a committed board, including an archived board. The operation locks the caller's user before the source board, checks read permission under the source lock, loads the snapshot and contiguous ordered updates through locked `latest_seq`, validates and projects the document, remaps every live graph ID and reference, and hydrates one sequence-zero snapshot. The new board is private, caller-owned, and has no copied membership or update/receipt history. Invalid source content fails before a board or idempotency receipt is written.

Two A27 orders were exercised with real Better Auth cookies and separate PostgreSQL connections. With the durable update paused just before commit, the archive waits for the board lock; the update commits at sequence 1, then archive commits. With the update paused after validation, archive commits first; the resumed update is rejected and leaves sequence, update rows, receipts, and accepted state unchanged. The second barrier is before the update transaction begins, so it proves the post-archive recheck but does not itself observe a blocked PostgreSQL row-lock wait. The later P3-12 gate will repeat both orders with its full concurrency harness.
