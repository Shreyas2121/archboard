## Behavior proved

An active board's owner can create editor or viewer invitations with 32 random bytes encoded as a canonical base64url token. The database stores only its SHA-256 digest. PostgreSQL sets expiry exactly seven days after creation. The initial authorized creation response contains the URL; an idempotent replay within the receipt window returns the same invitation with `inviteUrl: null` and `inviteUrlAvailable: false`. Owners can page through safe invitation metadata and revoke unused invitations while retaining audit rows. Scoped invite IDs cannot disclose another board's invitation.

Signed-in users can preview only the board title, inviter name, invited role, and expiry. Missing, malformed, and revoked tokens return `INVITE_UNAVAILABLE`; expired tokens return `INVITE_EXPIRED`; an accepted token returns `INVITE_EXHAUSTED` to another user. Acceptance locks the board before the invitation, rechecks its state, and inserts or upgrades membership without demoting an editor. Owner acceptance records the owner without creating a membership row. The recorded user can retry and receive the current effective role. Archived boards block listing, mutation, and acceptance until restored.

The A19 race test starts two different authenticated users on independent PostgreSQL transactions, synchronizes them before the board lock, and proves exactly one acceptance wins. The loser receives exhaustion, exactly one membership row is written, and the winner's retry is stable. Forced member-insert and receipt-insert failures roll back the invitation state and associated writes.

## Database and security evidence

The HTTP suite creates a process-unique schema, applies the committed migration with synchronization disabled, and drops the schema afterward. It checks digest-only storage, exact lifetime, idempotency receipt redaction, safe list and preview fields, cross-board isolation, role upgrade and non-demotion, owner absence from member rows, revoke/expiry/archive behavior, and rollback after forced failures. Console log, warning, and error spies check that the raw token, digest, token request body, and token-bearing URL are absent from captured logs. The database and replay response contain no raw token.
