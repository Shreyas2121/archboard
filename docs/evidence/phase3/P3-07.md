## Behavior proved

Every reader can list the board owner and members as safe user summaries with role and join time. The owner is synthesized from the immutable board owner field and is never inserted as a membership row. The response omits email, provider accounts, and invitation data. Owner-only role changes update an existing editor/viewer row under the board lock, preserve its join time, and cannot create duplicates. Owners can remove another member; editors and viewers can leave themselves. Owner self-removal, owner demotion, editor management, unauthenticated and unrelated access, archived mutation, and role values outside editor/viewer are denied. A scoped owner delete of an absent member is a 204 no-op and does not affect membership on another board.

Two deterministic write-order tests use real Better Auth cookies and independent PostgreSQL transactions. When an editor's validated graph update is held before its transaction and owner removal commits, the resumed write receives `NOT_FOUND` and does not advance sequence. When an editor's graph update holds the board lock before commit, an owner role change is started; the write commits first at sequence 1, the demotion then commits, and the next write is forbidden. The role and removal paths use the same shared board permission service as durable graph acceptance.

## Contracts used

Strict shared board/member path, role-change, member, collection envelope, user summary, and API error schemas; P3-04 effective-role and archive decisions; P3-03 explicit board transactions; and P3-02 session actor. User IDs remain opaque text. Owner membership is represented by `boards.owner_user_id`; member rows permit editor/viewer only.

No migration, direct member-add endpoint, invitation implementation, frontend, or room behavior was added.

## Database evidence

The HTTP suite creates a process-unique schema, applies the committed migration with synchronization disabled, and drops its schema afterward. Member list and mutations run through transaction-scoped board authority. Tests verify unchanged member join time and row count on role change, owner absence from member rows, no cross-board target mutation, active/archive behavior, and owner/member removal rules. The write-order tests use the durable-update harness with database-backed board locks and inspect the resulting sequence. The full P3-12 concurrency gate will repeat role/remove races alongside receipt and update-row assertions.

## Authentication and security evidence

Every HTTP role uses a real Better Auth `HttpOnly` cookie. The durable-update harness resolves its actor through the application's `RequestActor` from that cookie. Member responses expose only ID, name, image, role, and join timestamp; nonmembers see 404. No cookie, provider token, email address, or database URL is stored in response or evidence.
